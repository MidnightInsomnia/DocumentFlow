# DocumentFlow

**Состав репозитория:** исходники API, Worker и React-интерфейса, миграции, скрипты запуска, синтетические исследовательские наборы с манифестами, сохранённые результаты сравнений, протоколы проверок и лицензионные уведомления. Рабочая база, пользовательские оригиналы документов, локальные модели и секреты не публикуются. Для запуска по Docker используйте инструкции ниже и заполните собственный `.env` по `.env.example`. Исторические отчёты фиксируют состояние на момент их создания, а не результат проверки текущего коммита.

DocumentFlow — приложение на .NET 10, PostgreSQL и React для загрузки,
автоматической обработки и ручной проверки документов. Реестр поддерживает
серверный Global Search по имени файла, структурированным реквизитам и
распознанному тексту, а также фильтры, сортировку и пагинацию. На карточках
доступны вычисляемые связи, карточка контрагента по структурированному ИНН,
возможные повторы счетов и диагностические проверки актов. Документы со статусом
`Failed` можно вручную повторно поставить в очередь со страницы документа.

## Быстрый запуск Windows

Перед первым запуском установите Docker Desktop, .NET 10 SDK, Node.js и
`dotnet-ef`. Для OCR отсканированных документов дополнительно установите
Tesseract 5.x с языками `rus` и `eng`.

Запустите `RUN.bat` из корня проекта. Скрипт проверит зависимости, поднимет
PostgreSQL, дождётся его готовности, применит migrations, соберёт backend и
запустит API, Worker и React в отдельных окнах. После readiness автоматически
откроется `http://localhost:5173/documents`.

Скопируйте `.env.example` в `.env` **до первого запуска** и замените
`POSTGRES_PASSWORD` и остальные обязательные placeholders на локальные значения.
Если `.env` отсутствует, `RUN.bat` создаст его из примера, но до заполнения
секретов запуск API не завершится. Перед запуском API задайте `Auth__Jwt__Issuer`,
`Auth__Jwt__Audience`, случайный секрет `Auth__Jwt__SigningKey` не короче
32 байт UTF-8 и `Auth__Jwt__LifetimeMinutes`. Для самой первой загрузки пустой
БД задайте `Auth__BootstrapAdmin__UserName`, `Auth__BootstrapAdmin__Password`,
`Auth__BootstrapAdmin__DisplayName` (email необязателен). Оставлять bootstrap
пароль после создания администратора не требуется: повторный запуск его не
сбрасывает. Секреты храните только локально, не коммитьте `.env` и не пишите
их в логи. Для остановки выполните `STOP.bat`; PostgreSQL volume и
загруженные документы при этом не удаляются.

Tesseract является необязательной runtime-зависимостью. Без него работают PDF с
текстовым слоем и DOCX с извлекаемым текстом, но OCR отсканированных PDF,
JPG/JPEG, PNG и TIFF недоступен (обработка завершится ошибкой). RUN покажет
предупреждение, но продолжит запуск MVP.

**Поддерживаемые входные форматы:** PDF с текстовым слоем или сканированный PDF
(через OCR), DOCX (текст и таблицы Open XML), JPEG/PNG/TIFF (OCR через Tesseract).
TIFF может содержать одну или несколько страниц: страницы в исходном порядке
декодируются в PNG в памяти, поворачиваются согласно EXIF orientation и передаются
существующему OCR (`rus+eng` в стандартной конфигурации). Встроенный просмотр
показывает TIFF по страницам, не изменяя оригинал. Ограничения TIFF: не более
30 страниц, 6000 пикселей по любой стороне, 12 млн пикселей на страницу и
48 млн пикселей суммарно; общая граница файла — 20 МиБ. Форматы `.doc`, RTF,
XLS/XLSX не поддерживаются. DOCX извлекает обычные абзацы и строки таблиц
с сохранением порядка ячеек; встроенный preview показывает оригинальную
разметку, включая изображения, если их отображает локальный `docx-preview`.
**OCR текста внутри встроенных изображений DOCX не выполняется.** DOCX без
извлекаемого текста не считается повреждённым: он получает отдельную ошибку.
Production-классификация и извлечение полей используют отдельные классы;
замороженные правила Research/Evaluation сохраняются без изменений.
TIFF-декодер использует managed `BitMiracle.LibTiff.NET` 2.4.660 (BSD-3-Clause с сохранёнными libtiff/IJG notices); PNG формируется средствами .NET. ImageSharp и Magick.NET удалены. Обычный TIFF поддержан, BigTIFF отклоняется с явным сообщением. Подробности и лицензии — в `docs/TIFF-DEPENDENCY-CHANGE.md`.

## Загрузка документов

`POST /api/documents` принимает один файл в поле `File` формата PDF, DOCX,
TIFF (`.tif`/`.tiff`, `image/tiff` или `image/tif`), JPG/JPEG или PNG.
Максимальный размер — 20 МиБ. Принятые файлы сохраняются под
сгенерированными именами в `storage/documents`; этот каталог не публикуется как
статические файлы и исключён из Git.

Страница загрузки поддерживает одновременный выбор до 20 документов общим
размером до 100 МиБ. Каждый файл загружается независимым запросом, получает
отдельный `Document` и ставится в общую очередь обработки; одновременно
выполняется один upload-запрос, чтобы первый выбранный файл сохранял приоритет
при одинаковых байтах.

При загрузке вычисляется SHA-256 исходных байтов файла. Повторная загрузка
идентичных байтов отклоняется (`409`, `code: document_duplicate`) независимо от
имени файла; **при загрузке** текст и реквизиты не сравниваются. Отдельная
диагностика возможных повторов по реквизитам выполняется после обработки.
Ответ при точном совпадении содержит
`existingDocument.id`, `existingDocument.fileName` и `existingDocument.isArchived`.
Защита от конкурентных
загрузок обеспечена уникальным индексом PostgreSQL по ненулевому `ContentHash`.
При дубликате новая запись и событие не создаются. Интерфейс показывает
имя исходного документа и ссылку для его открытия; если он в архиве,
интерфейс сообщает об этом и позволяет перейти к восстановлению. Архивный
документ остаётся дубликатом: новую копию загрузить нельзя. Дубликат не
считается ошибкой всей группы файлов.
У прежних документов `ContentHash = NULL`: они не участвуют в обнаружении
дубликатов, пока хэш не заполнен; массового backfill при запуске нет.

Для backend-клиентов доступен `POST /api/documents/batch` с несколькими полями
`Files`: HTTP `200` содержит массив `items` со статусом каждого файла
`uploaded`, `duplicate` (с `existingDocumentId`, `existingFileName` и
`existingIsArchived`) или
`failed`. Ошибка одного файла не отменяет остальные. Текущий frontend
по-прежнему отправляет отдельные запросы последовательно,
показывает для каждого результат и сводку загруженных, дубликатов и ошибок.

## Маршрутизация документов

Маршрутизация задаётся разделом `Routing` в `src/DocumentFlow.Api/appsettings.json`
и `src/DocumentFlow.Worker/appsettings.json` (тип документа → подразделение):

```json
"Routing": {
  "Invoice": "Accounting",
  "Act": "Accounting",
  "Contract": "Legal"
}
```

`Unknown` всегда остаётся `Unassigned` и не требует записи в конфигурации.
Отсутствие обязательного типа или неизвестное подразделение останавливает запуск
API/Worker с указанием проблемного типа и значения. Можно переопределить значения
переменными среды, например `Routing__Contract=Accounting` (при запуске через
`RUN.bat` — также через корневой `.env`); после изменения перезапустите приложение.
Новая конфигурация применяется к новым документам и к подтверждённой ручной
проверке; уже назначенное подразделение архивного документа не меняется при
архивировании или восстановлении. UI не редактирует маршруты.

## Архивирование документов

Admin и Operator могут перемещать завершённые (`Completed`), ожидающие ручной
проверки (`NeedsReview`) и завершившиеся ошибкой (`Failed`) документы в архив
со страницы документа (`POST /api/documents/{id}/archive`), а затем возвращать
их (`POST /api/documents/{id}/restore`). Повторная архивация и восстановление
активного документа возвращают `409`; `PendingProcessing` и `Processing`
архивировать нельзя. Это отдельное состояние: статус обработки не меняется и
после восстановления остаётся прежним. В истории сохраняются события
`DocumentArchived` и `DocumentRestored` с именем и ID действовавшего пользователя.

Архивирование не удаляет оригинальный файл, извлечённый текст, поля, историю,
preview или `ContentHash`. Архивные документы по умолчанию скрыты из рабочего
реестра и исключены из рабочих показателей Dashboard; фильтр реестра
«Активные / Архивные / Все» выполняется сервером вместе с поиском, остальными
фильтрами, сортировкой и пагинацией. Dashboard показывает отдельное число
архивных документов. По прямой ссылке архивный документ доступен для просмотра,
но повторная обработка, ручная проверка и AI-подсказка до восстановления
недоступны. Оригинал остаётся на месте, поэтому точная бинарная копия архивного
документа по-прежнему определяется как дубликат.

## Локальный запуск

Скопируйте `.env.example` в `.env` и задайте пароль PostgreSQL. Для API и Worker
реальный секрет задавайте через user secrets или переменную окружения
`ConnectionStrings__Postgres`.

## Вход, роли и аудит

API документов и Dashboard требуют JWT Bearer. Публичны только
`POST /api/auth/login` и health endpoints. Публичной регистрации нет.
После первого запуска войдите через `/login` учётной записью bootstrap Admin;
создайте Operator на странице «Пользователи» (доступна только Admin).
Admin также может создавать пользователей, менять роль, активность и задавать
новый пароль. Operator может работать с документами и AI-подсказками, но не
управлять пользователями. У пользователя ровно одна роль — Admin или Operator;
последнего активного Admin нельзя отключить либо понизить в роли.

JWT живёт `Auth__Jwt__LifetimeMinutes` минут. Пароль обрабатывает ASP.NET Core
Identity; неверные попытки входа временно блокируются. Изменение пароля, роли
или статуса аккаунта инвалидирует ранее выданные JWT. При logout браузер
удаляет токен из `sessionStorage`; чтобы продолжить работу, войдите заново.
`GET /api/auth/me` возвращает текущего пользователя, а
`POST /api/auth/change-password` требует старый и новый пароль.
API управления: `GET/POST /api/admin/users`, `PUT /api/admin/users/{id}/role`,
`PUT /api/admin/users/{id}/active`, `POST /api/admin/users/{id}/reset-password`.
В Development доступна спецификация `GET /openapi/v1.json` с Bearer-схемой;
она требует JWT. **Swagger UI в проекте нет**, поэтому интерактивная кнопка
Authorize недоступна. Токен не публикуйте.

История документа сохраняет `ActorUserId` и снимок `ActorDisplayName` для
загрузки, ручной проверки, повторной обработки и запроса AI-подсказки.
Автоматические события Worker и старые записи имеют пустого actor и
показываются как «Система». Событие запроса AI не хранит prompt, OCR-текст
или ответ модели; ручная проверка фиксирует лишь имена изменённых полей.

## Конфигурация

Основные переменные окружения:

- `ConnectionStrings__Postgres` — connection string PostgreSQL для API и Worker;
- `DocumentStorage__RootPath` — один и тот же абсолютный каталог файлов для API
  и Worker;
- `Tesseract__ExecutablePath` — executable Tesseract (по умолчанию `tesseract`);
- `Tesseract__Languages`, `Tesseract__PageSegmentationMode` и
  `Tesseract__TimeoutSeconds` — параметры OCR;
- `VITE_API_BASE_URL` — адрес API для frontend.

Docker Compose автоматически читает корневой `.env`. Обычный `dotnet run` не
обязан импортировать его значения в переменные окружения, поэтому параметры .NET
нужно задавать отдельно. Пример ручного запуска в Windows PowerShell:

```powershell
$env:ConnectionStrings__Postgres="Host=localhost;Port=5432;Database=documentflow;Username=documentflow;Password=change_me"
$env:DocumentStorage__RootPath="C:\...\documentflow\storage\documents"
$env:Tesseract__ExecutablePath="tesseract"

dotnet run --project src/DocumentFlow.Api
dotnet run --project src/DocumentFlow.Worker
```

Оба процесса должны получать одинаковые `ConnectionStrings__Postgres` и
`DocumentStorage__RootPath`. Значение `change_me` здесь является только
демонстрационным placeholder и должно быть заменено локальным секретом.

Если порт `5432` занят, в `.env` можно указать:

```dotenv
POSTGRES_PORT=15432
```

Тогда в `ConnectionStrings__Postgres` для API и Worker также необходимо указать
`Port=15432`. Свободный порт автоматически не выбирается.

```bash
docker compose up -d
dotnet build
dotnet run --project src/DocumentFlow.Api
dotnet run --project src/DocumentFlow.Worker
```

Пример загрузки после входа через `POST /api/auth/login` (подставьте выданный JWT):

```bash
curl -H "Authorization: Bearer <JWT>" -F "File=@invoice.pdf;type=application/pdf" http://localhost:5214/api/documents
```

Черновик реквизитов: `GET/PUT /api/documents/{id}/review/draft`. При PUT передайте `baseVersion` документа и `expectedDraftUpdatedAtUtc` точно из последнего GET/успешного PUT; для первого черновика — `null`. Это две независимые проверки: версии документа и редакции черновика. Сохранение устаревшего черновика возвращает 409 с кодом `review_draft_conflict`. Null-значения полей нормализуются в пустые строки; незаполненные и ещё не прошедшие валидацию значения можно сохранить.

Основные endpoints:

- `POST /api/documents` — загрузить документ (`202`, при ошибке запроса `400`,
  при точном бинарном дубликате `409` с `code: document_duplicate`).
- `POST /api/documents/batch` — независимая загрузка файлов с результатом
  для каждого (`200`, статусы `uploaded`/`duplicate`/`failed`).
- `GET /api/documents` — получить paged list; доступны фильтры `status`, `type`,
  `department`, поиск `search` по имени файла и полю `Number`, диапазон
  `createdFrom`/`createdTo`, сортировка `sortBy`/`sortDirection`, а также `page`
  и `pageSize` (`200` или `400`).
- `GET /api/documents/{id}` — получить details с распознанным текстом, полями и
  событиями (`200` или `404`). Внутреннее имя сохранённого файла не возвращается.
- `GET /api/documents/{id}/file` и `/file/download` — получить исходный документ.
- `GET /api/documents/{id}/preview/pages` — число страниц TIFF (`{ "pageCount": N }`);
  `GET /api/documents/{id}/preview/pages/{page}` — PNG указанной страницы
  (нумерация с 1). Просмотр формируется из сохранённого файла по Document Id,
  не создаёт постоянных копий и не меняет исходник. Повреждённый TIFF даёт `422`.
- `POST /api/documents/{id}/review` — вручную проверить документ в
  `NeedsReview` (`200`, `400`, `404`, `409` или `422`).
- `POST /api/documents/{id}/review/ai-suggestion` — необязательная подсказка
  при ручной проверке (если локальный AI включён и доступен).
- `GET /api/documents/{id}/review-context` — данные и причины ручной проверки;
  `POST /api/documents/{id}/retry` — повторная обработка допустимого `Failed`.
- `POST /api/documents/{id}/archive` и `/restore` — архивирование и восстановление.
- `GET /api/documents/{id}/related` — вычисленные связи Act ↔ Contract по номеру,
  включая неоднозначные и архивные совпадения.
- `GET /api/counterparties/{inn}` — карточка по сохранённому структурированному ИНН.
- `GET /api/documents/{id}/potential-duplicates` — возможные повторы Invoice по
  ИНН + номеру + дате (не блокирует загрузку и не заменяет SHA-256).
- `GET /api/documents/{id}/consistency-checks` — диагностические предупреждения
  для Act; отсутствие предупреждений не является юридическим подтверждением.
- `GET /api/dashboard` — получить агрегированную статистику Dashboard (`200`).

Health endpoints:

- `GET /health/live` — процесс API работает; зависимости не проверяются;
- `GET /health/ready` — PostgreSQL и document storage доступны;
- `GET /health` — alias readiness для совместимости.

Healthy readiness возвращает HTTP `200`; недоступность хотя бы одной зависимости
возвращает HTTP `503` с кратким JSON-описанием checks.

Пример ручной проверки:

```json
{
  "type": "Invoice",
  "fields": [
    { "name": "Number", "value": "125" },
    { "name": "Date", "value": "2026-09-17" },
    { "name": "INN", "value": "7712345678" },
    { "name": "Amount", "value": "125000.50" }
  ]
}
```

Новый клиент передаёт `expectedVersion` из текущего `GET /api/documents/{id}`.
`409` также означает устаревшую версию: перечитайте документ, не перезаписывайте чужие изменения.
`409` означает, что документ уже не находится в `NeedsReview`; `422` — что
ручные данные не прошли бизнес-валидацию и не были сохранены.

## Фоновая обработка

Worker выбирает документы со статусом `PendingProcessing` и выполняет полный
processing pipeline. Захват выполняется атомарно в PostgreSQL через
`FOR UPDATE SKIP LOCKED`, поэтому несколько Worker могут безопасно обрабатывать
разные документы параллельно. Для обычных PDF с текстовым слоем Worker извлекает
текст через PdfPig и сохраняет его в `Documents.ExtractedText`. PDF-сканы
рендерятся через PDFtoImage и распознаются локальным Tesseract; JPG/PNG также
передаются в Tesseract.

Для OCR требуется Tesseract 5.x с языками `rus` и `eng`. В Linux обычно нужны
пакеты `tesseract-ocr`, `tesseract-ocr-rus` и `tesseract-ocr-eng`. Executable
должен быть доступен через `PATH`; альтернативный путь задаётся настройкой
`Tesseract:ExecutablePath`. Приложение не устанавливает системные зависимости
автоматически.

После извлечения текста DocumentFlow автоматически классифицирует документ как
`Invoice`, `Contract`, `Act` или `Unknown`. На текущем этапе используется
детерминированный `ProductionRuleBasedDocumentClassifier`; исследовательские
Rules v1/v2 остаются замороженными. LLM не участвует в основном pipeline.

Для известных типов rule-based extraction сохраняет структурированные реквизиты:

- `Invoice`: `Number`, `Date`, `INN`, `Amount`, необязательный `KPP`;
- `Contract`: `Number`, `Date`, необязательный `Amount`;
- `Act`: `Number`, `Date`, `Amount`, необязательный `RelatedContractNumber`.

Поддерживаются распространённые цифровые даты. ИНН и КПП берутся только после
явных маркеров, сумма договора — после метки цены/стоимости договора, а номер
связанного договора акта — после формулировки «к договору» или «по договору».
Отсутствие необязательного реквизита не требует ручной проверки, но извлечённое
необязательное поле проходит обычную проверку значения и confidence.

После extraction результат проходит rule-based validation. Статус `Completed`
означает, что тип документа поддерживается, все обязательные поля присутствуют,
их значения прошли базовые проверки, а confidence не ниже `0.80`.
`NeedsReview` устанавливается для типа `Unknown`, отсутствующего обязательного
поля, некорректного значения или confidence ниже порога. Технические ошибки
по-прежнему приводят к `Failed`. Ручное исправление выполняется через API или
frontend и повторно запускает validation и routing.

После успешной validation документ автоматически маршрутизируется по разделу
`Routing` (по умолчанию `Invoice` и `Act` — в `Accounting`, `Contract` — в
`Legal`). Для `Unknown` и документов со
статусом `NeedsReview` отдел остаётся `Unassigned`. На текущем этапе routing
означает только установку `TargetDepartment` внутри системы, без уведомлений и
внешних интеграций.

Итоговые статусы различаются следующим образом:

- `Completed` — автоматическая либо подтверждённая ручная обработка и
  маршрутизация успешно завершены.
- `NeedsReview` — техническая обработка завершилась, но результат требует
  проверки человеком.
- `Failed` — произошла техническая ошибка обработки.

Автоматический workflow: `PendingProcessing → Processing → Completed`,
`NeedsReview` либо `Failed`. Ручной workflow: NeedsReview → corrections →
validation → routing → Completed. Ручное изменение поля отключает проверку
extraction confidence для этого поля, но не отключает проверку его значения.

## Frontend

Frontend создан на React, TypeScript и Vite. Он предоставляет реестр с
серверным Global Search, фильтрами, сортировкой и пагинацией, загрузку документов,
карточки с диагностическими блоками и связями, архивирование/восстановление,
polling статуса и форму ручной проверки `NeedsReview`.

Для документов `NeedsReview` интерфейс показывает исходный документ, причины
ручной проверки, confidence классификации и извлечённых данных, проблемные поля
и форму корректировки без дублирования backend validation rules.

Опциональная AI-подсказка для ручной проверки запускается только пользователем
и доступна при `AiReview__Enabled=true`. Она использует локальный Ollama,
показывает предлагаемый тип и поля, но ничего не сохраняет до обычного ручного
подтверждения. Production pipeline использует отдельные production Rules и не зависит
от Ollama. Настройка, API-контракт и гарантии read-only описаны в
[`docs/ai-assisted-review.md`](docs/ai-assisted-review.md).

Для обычного запуска в Windows добавьте параметры в корневой `.env`:

```text
AiReview__Enabled=true
Ollama__BaseUrl=http://localhost:11434
Ollama__Model=qwen2.5:7b-instruct
Ollama__TimeoutSeconds=120
```

После этого запустите `RUN.bat`. Windows launcher прочитает параметры и передаст
их API. Ollama остаётся внешней необязательной зависимостью: launcher не
запускает и не скачивает Ollama или модели, а недоступность Ollama не мешает
запуску DocumentFlow и обычной ручной проверке.

Страница `/dashboard` показывает общее количество документов, распределение по
статусам, типам и отделам, автоматическое и ручное завершение, доли ручной
проверки и ошибок, а также активность за последние семь UTC-дней.

```bash
cd frontend/documentflow-web
npm install
npm run dev
```

Frontend доступен по адресу `http://localhost:5173`, API — по адресу
`http://localhost:5214`. При запуске через `RUN.bat` frontend получает URL
API из локального `.env` (по умолчанию `http://localhost:5214`):

```bash
VITE_API_BASE_URL=http://localhost:5214
```

Итоговый flow: upload → PDF text/OCR или DOCX extraction → classification →
field extraction → validation → routing → `Completed`. Документы с недостаточными данными переходят
в `NeedsReview`, исправляются в React и после повторной validation/routing
завершаются. Технические проблемы приводят к `Failed`. После появления структурных
полей карточка показывает вычисленные связи, возможные повторы Invoice и
диагностические предупреждения Act без автоматического изменения статуса.

## Известные ограничения

- OCR рассчитан на печатный текст и не гарантирует распознавания рукописного;
  изображения внутри DOCX не распознаются.
- Блокирующий точный бинарный дубликат определяется только по SHA-256 исходных
  байтов; прежние документы без `ContentHash` могут не распознаться этим механизмом.
  Отдельный **Potential Business Duplicate** для Invoice — информационный сигнал
  по структурированным ИНН, номеру и дате, а не доказательство повторной операции.
- Вычисленная связь Act → Contract и consistency warnings не являются
  юридической или бухгалтерской экспертизой. Карточка контрагента учитывает
  только документы с сохранённым структурированным ИНН; полнота истории других
  типов документов не гарантируется.
- Routing — простое соответствие `DocumentType → Department`, без маршрутов
  согласования. Электронная подпись, email ingestion и внешнее ЭДО отсутствуют.
- AI-подсказка необязательна и зависит от локального Ollama; результат сохраняет
  только пользователь при обычной ручной проверке.

| [`corpus-v3-final-holdout`](evaluation/corpus-v3-final-holdout/README.md) | 72 | 208 | Независимый финальный holdout для замороженных стратегий v2 |

Манифесты — `evaluation/<набор>/manifest.json`; бинарные контрольные суммы и правила заморозки v3 — рядом с его README. Карта канонических и исторических результатов: [`evaluation/ARTIFACT-INDEX.md`](evaluation/ARTIFACT-INDEX.md). Отчёты по v3 — `evaluation/final-results/v3/`, более ранние — `evaluation/baselines/`, `evaluation/holdout-results/` и `evaluation/development-results/`. Не складывайте новые результаты поверх зафиксированных каталогов. **Известное расхождение исходного архива:** все 42 бинарных файла v2 совпадают с `FILES-SHA256.txt`, однако текущий `corpus-v2-holdout/manifest.json` не совпадает с историческим SHA-256, записанным в его `ERRATA.md`; этот хеш нельзя выдавать за подтверждённый. Данные и исторические результаты ради подгонки хеша не изменялись. Для v3 содержимое `manifest.json`, `FILES-SHA256.txt` и `CORPUS-SPEC.md` сохраняется с теми байтами, к которым привязаны хеши в `FREEZE.md`.

Для **отдельно санкционированного** исследовательского прогона на компьютере с .NET 10 SDK, Tesseract с `rus+eng` и установленными зависимостями:

```bash
dotnet run --project tools/DocumentFlow.Evaluation -- --corpus evaluation/corpus-v3-final-holdout --output evaluation/results --strategy rules
```

`evaluation/results/` исключён из Git: каждый запуск создаёт там новый каталог с отчётом. Укажите `Tesseract__ExecutablePath` и `Tesseract__Languages=rus+eng`, если движок не доступен из PATH; проверьте языки командой `tesseract --list-langs`. Для стратегий с LLM дополнительно нужен **локальный** Ollama и подходящая модель, см. [`evaluation/README.md`](evaluation/README.md). Без OCR документы со сканами могут быть пропущены — такой результат нельзя выдавать за полный прогон. В этом коммите исследовательский CLI **не запускался**; опубликованы ранее сохранённые артефакты, а не новые метрики.

Автоматические unit/frontend/integration-тестовые проекты в выбранной более свежей рабочей копии отсутствуют; здесь находятся исходники приложения, синтетические файлы для оценки и исторические протоколы сценарных проверок. Простая успешная сборка не означает прохождения тестов. В этой публикации проверялись только чистая сборка .NET-решения и сборка frontend (`npm ci`, `npm run build`); полноценный новый прогон корпусов и автоматические тесты не выполнялись.

### Границы воспроизводимости и приватность

`docs/verification/` и `evaluation/` — **исторические** свидетельства, со своими датами и ограничениями; не подменяйте их новой проверкой текущих изменений. Отчёты описывают часть окружения (например, CPU/RAM/GPU для одного сравнения), но полного протокола аппаратуры, точной сборки Tesseract и происхождения языковых моделей для каждого числа времени нет. Не делайте из опубликованных таймингов универсальный benchmark. В документах о старой рабочей копии абсолютные пути к персональному профилю обезличены; они не являются рабочими путями для клонированного проекта.

Не публикуются `.env`, локальные пароли и JWT-ключи, PostgreSQL `pgdata`, пользовательские документы, локальные модели Ollama, журналы runtime, `node_modules`, `bin` и `obj`. Их нужно подготовить отдельно по инструкциям выше. Синтетические корпуса можно использовать для оценки, но нельзя подменять ими проверку на реальных документах без соответствующего разрешения и защиты данных.
